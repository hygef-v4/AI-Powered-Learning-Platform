## Findings requiring attention

### P2 — U13 cross-subject negative test can pass for the wrong reason (weak assertion/fixture)

`backend/src/test/java/edu/aiplatform/materials/application/MaterialModuleServiceTest.java:52–56`, `attachRejectsQuizOfAnotherSubject`, mocks `MaterialAccessPolicy`, leaves `canManageQuiz` false by default, and accepts any `ApiException`. Source `MaterialModuleService.java:120–125` first rejects cross-subject with `MATERIAL_QUIZ_INVALID` (400), then separately rejects lack of quiz management permission with `MATERIAL_QUIZ_NOT_FOUND` (404). If the subject-equality guard were removed, this test would still pass at the permission guard. It therefore does not establish BR-U13-M03 (business-rules.md:61), despite its name. Stub management permission to true for the foreign quiz and assert the exact subject-mismatch code/status, while retaining the no-link assertion. This is a concrete non-discriminating test, not a proven production defect.

### P2 — U11 documentation and frontend test intentionally disagree about blocked reasons (doc-code mismatch)

BR-U11-03 (`u11-quiz-practice/functional-design/business-rules.md:18`) says a quiz that cannot be started should explain why. `frontend/src/features/quizpractice/QuizPracticeScreens.test.tsx:78–89` explicitly requires the exhausted-attempt reason to be absent, even though fixture `DETAIL.blockedReason` contains it at line 48. Production `QuizPracticeDetailPage.tsx:106–107` and `:127–134` deliberately hides unavailable actions without explanation. The test accurately protects current UI, but cannot count as verifying this documented clause. Resolve intended behavior in docs/UI before changing the test oracle.

### P2 — U12 leader rename is implemented/tested but absent from the main authorization rule (doc-code mismatch)

BR-U12-01 (`u12-group-assignment/functional-design/business-rules.md:16`) says only the main teacher creates/edits groups. Source `backend/src/main/java/edu/aiplatform/groups/application/GroupRenameService.java:42–77` allows an active current student leader to rename their group in an OPEN class, with name checks, version bump and audit. `GroupRenameServiceTest.java:61–84` and frontend `MyGroup.test.tsx:59` affirm that behavior. Source Javadoc at `GroupRenameService.java:22–24` explicitly records the 2026-10-29 requirement. Add the narrow student-leader rename exception to the BR rather than treating these tests as stale.

### P2 — U11 result retry availability misses retired/closed state (production/doc mismatch exposed by a coverage gap)

BR-U11-02 (`business-rules.md:17`) limits RETIRED quizzes to reviewing prior attempts; BR-U11-03 requires OPEN for starting. `QuizAttemptService.java:150–152` computes `canRetry` only from the attempt snapshot's maximum and total attempts; it does not check current quiz/class status. `frontend/src/features/quizpractice/QuizResultPage.tsx:55` renders the retry button directly from that flag. A result of a retired quiz can therefore advertise retry while `start` rejects at `QuizAttemptService.java:65–67`. The retirement test `QuizPracticeServicesTest.java:364–369` only checks auto-submit mode/status; retired history test `:373–385` checks history `canStart`, not result `canRetry`. Add a result assertion after changing fixture `quizStatus` to RETIRED, plus a closed-class counterpart and a settings-limit-change case. Source-observed defect; not runtime-reproduced here.

### P2 — U12 submission protections have happy-path tests but no direct conflict/resubmit assertions (coverage gap)

BR-U12-40–43 (`business-rules.md:59–62`) rely on guarded snapshots and repeat submissions. `GroupSubmissionService.java:89–90` rejects stale/null document version, `:175–176` rejects a lost document CAS, `:127–132` closes without submitting if unchanged since last submit, and `:98–99` leaves manual submissions editable for resubmission. Existing `GroupSubmissionServiceTest.java:109–182` covers initial manual snapshot, member rejection, invalid document, auto finalization, already-CLOSED no-op and retired mode. It does not drive stale-version or lost-CAS branches, second manual submission/old snapshot immutability, or unchanged-since-last-submit closure. Prioritize assertions that failure does not call evaluation/publish success, a second submission replaces only current receipt, and unchanged auto-close does not produce a new evaluation/event. The same-call `verify(evaluation)` at test line 128 establishes collaboration, not actual transactional rollback across U09; retain an integration boundary for that guarantee.

### P2 — U13 module extension needs additional negative/visibility branches (coverage gap)

The complete six-case `MaterialModuleServiceTest.java:38–78` covers active-material deletion block, archived-material move, stale supplied delete version, foreign-subject attach, attach move and student open-list filtering. It does not cover BR-U13-M01/M04/M05/M06 (`business-rules.md:59–64`) branches:

- Last module with archived material: source `MaterialModuleService.java:72–75`; assert `MATERIAL_MODULE_LAST`, no move/delete.

- Rename/reorder repository CAS false, duplicate IDs, foreign-subject IDs and stale item version: source `:60–64` and `:81–95`. The material reorder tests in `MaterialServiceTest.java:70–77` exercise material ordering, not module ordering.
- Subject view excludes class quizzes (`:32–36`); teacher class view includes subject OPEN/RETIRED but excludes subject DRAFT and other class quizzes (`:46–48`); independent `canManageModules` vs `canManageQuiz` projection (`:139–142`). Current student test checks `canManage=false`, but cannot verify those teacher/manager distinctions.
- Migration uniqueness/cascade/backfill constraints from M02/M03/M04 have no module-specific repository integration test in this inventory. Unit mocks cannot establish those SQL guarantees.

### P2 — U14 announcement email flag matrix is only partially asserted (coverage gap)

BR-U14-03/20 (`business-rules.md:18,39`) requires email only for important + sendEmail. Source `RecipientResolver.java:21–24` has the conjunction. `RecipientResolverTest.java:21`, despite its broad name, asserts only author exclusion with both flags true and null email for important=false/sendEmail=true. It never asserts `emailType=ANNOUNCEMENT_IMPORTANT` for both true with a non-author recipient or null for important=true/sendEmail=false. The producer test `AnnouncementServiceTest.java:25` verifies sendEmail in the event, not the recipient resolver output; email preference tests use type strings directly. Add explicit resolver matrix and recipient assertions. No stale required-reason tests were found.

### P2 — U15 new activity API lacks the contract assertions already present for dashboard/backups (coverage gap)

Activity extension is documented in `u15-admin-dashboard/functional-design/business-rules.md:44`; controller `AdminDashboardController.java:36–41` separately checks admin, rejects unknown query and emits no-store. `AdminDashboardApiContractTest.java:65–129` exercises dashboard/backups authorization and malformed query behavior but does not call `/activity`; `AdminDashboardControllerTest.java` also only covers dashboard/backups. Activity service test `AdminDashboardActivityServiceTest.java:111–115` merely accepts an `ApiException` for one TEACHER. Add direct `/activity` tests for ADMIN/no-store projection, all non-admin roles/anonymous, access-denied audit and no source reads, and unknown/duplicate query keys. Existing activity service tests provide meaningful algorithm evidence; avoid claiming the entire activity endpoint is untested.

### P3 — U11 hidden-result frontend fixture contradicts the backend contract (test-code mismatch)

`frontend/src/features/quizpractice/QuizPracticeScreens.test.tsx:50–55` defines both `showScore=false` and `showAnswers=false` but sets correctCount/wrongCount and per-question correct to non-null values. Backend `PracticeSupport.java:135–171` masks these when both flags are false, explicitly tested at `QuizPracticeServicesTest.java:285–305`. The hidden-result UI test consumes an impossible response; use null correctness/counts as its baseline, overriding only reveal-enabled cases. This does not by itself show a user-visible failure, but weakens frontend/backend contract fidelity.

### P3 — U12 optional rejection reason normalization/boundaries are weakly checked (coverage gap)

Current tests correctly reflect optional reasons: `LeaderRequestServiceTest.java:82–86` checks null request reason persisted as empty; `:136–146` checks null rejection reason accepted and decided requests rejected. Source `LeaderRequestService.java:62–64` and `:142–147` additionally normalize whitespace, enforce 1,000 characters and persist null for blank rejection reason. No existing tests assert the saved decisionReason is null for whitespace, retain/trim a nonempty rejection reason, accept 1,000 vs reject 1,001 rejection chars, or reject inactive proposed/approved members and archived decisions. Add focused assertions without reverting to required reasons. BR-U12-10/11 are at doc lines 28–29.

### P3 — U15 activity branch candidates beyond existing aggregation evidence (coverage gap)

`AdminDashboardActivityServiceTest.java:42–106` already checks Vietnam midnight active delta, 7 days with quiet-day zeros/out-of-range row, target-account fallback and unknown login, and an assignment source failure leaving siblings available. Source `AdminDashboardActivityService.java:83–90` additionally sums duplicate day/kind rows and ignores negative/unknown kinds; `:101–102` prefers actorEmail over target; `:108–112` treats null and mapping errors as unavailable. Add those cases and isolated failures/null for audit active change/security sources, explicitly checking UNAVAILABLE with data=null and other sections preserved. Timeout mechanics already have independent infrastructure evidence in `DashboardSourceReaderTest.java:16–85`; do not describe timeout handling as absent.
