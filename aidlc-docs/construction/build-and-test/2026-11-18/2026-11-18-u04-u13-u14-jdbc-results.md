## Hành vi đo trên code JPA và giữ lại

- `PESSIMISTIC_WRITE` của Hibernate 6.6 trên PostgreSQL là `for no key update`: `for key share` từ transaction khác không bị chặn, `for no key update` bị chặn. JDBC dùng đúng mệnh đề này cho U04 và `lockEmailDelivery`.
- Hibernate bỏ qua hint `jakarta.persistence.lock.timeout=2000` trên PostgreSQL. Khi caller không đặt `lock_timeout` (như `markEmailFailed`), lệnh khóa chờ tới khi hàng được nhả (đo 6.021 ms với holder giữ 6 s). JDBC không thêm timeout mới; test `emailRowLockAllowsKeyShareAndWaitsForTheHolderWithoutOwnTimeout` khóa hành vi này. `lockEmailBudget` vẫn đặt `lock_timeout` 2 s.

## Khác biệt và giới hạn

- **JD-08:** handler `PersistenceException` trong `NotificationExceptionHandler` không bao giờ chạy (lỗi JPA đã được dịch thành `DataAccessException`), nên bị bỏ thay vì đổi sang bắt `DataAccessException` → 503. Lỗi DB vẫn do `GlobalExceptionHandler` xử lý như trước; phản hồi API không đổi.
- **U04 trùng mã:** dò `SQLException` (state 23505, message chứa `"uk_subjects_code"`) thay `PSQLException` như kế hoạch, vì driver PostgreSQL có scope `runtime`.
- **U14 email:** JPA ghi thay đổi `EmailDelivery` khi flush/commit; JDBC ghi ngay bằng `updateEmailDelivery` ở mọi nhánh, kể cả trước khi ném `RetryableJobException` (transaction vẫn commit vì `noRollbackFor`). `lockEmailDelivery` đọc lại trạng thái mới sau khi có khóa; JPA trả lại instance đã quản lý trong `releaseDeferredEmails`.
- **Timeout:** `JdbcTemplate` áp thời gian transaction còn lại làm query timeout, giống Hibernate.
- **Môi trường:** Maven offline thiếu `jackson-bom 2.21.8` và `netty-bom 4.1.140.Final`, nên chạy online. Máy đang chạy hai stack Docker (`platform-*`, `conv041314-*`) không do phiên này khởi động. Hai test đo thời gian (`localOwnerReadLatency…`, `classEventCreates…Fanout…`) lúc đạt lúc trượt trên cả code JPA chưa đổi; không hạ ngưỡng.
- E2E API ghi ở mục dưới. Chưa chạy trên môi trường staging.
